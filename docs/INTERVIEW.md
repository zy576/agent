# 面试答辩速记

## 为什么这不是现成 Agent 的封装？

唯一远程调用是普通 Chat Completions。`CodingAgent` 自己保存消息、配对 `tool_call_id`、执行本地函数、把结果回传并决定何时停止；`ContextManager`、`ToolRegistry` 和重试逻辑也都在仓库中。

## 模型怎样“选择”工具？

程序默认把六个本地函数的 JSON Schema 随消息发送；启用只读子 Agent 后再增加一个 `delegate_readonly` 批量委派工具。模型返回函数名和 JSON 字符串参数，程序解析、校验并本地执行；模型看不到可直接控制的终端或文件系统。

## 为什么不用 shell 字符串？

普通可执行文件通过 `argv` 直接传给 `subprocess`，不解释管道和重定向。Windows 的 npm 等 `.cmd/.bat` 启动器会先通过 PATH 解析为绝对路径，并拒绝元字符参数。复杂流水线必须拆成多个进程调用。

## 坏 JSON、命令失败和网络错误怎么办？

坏 JSON、缺参、未知工具和路径策略错误都变成结构化 tool 结果，模型可修正。命令输出始终带 exit code。429/5xx 与短暂网络错误重试；4xx 参数或鉴权错误直接暴露安全错误信息，但不含 key。

## 如何判断任务完成？

模型无工具调用并给出最终报告是正常终止；但最后一次写入之后必须有一次成功命令验证。默认不设模型决策步数上限，让复杂任务持续到报告完成；相同调用重复四次、总工具调用量和总运行时间仍会硬熔断，显式传入 `--max-steps` 时也可启用有限步数模式。

## 上下文为什么不能简单删前半段？

OpenAI-compatible 协议要求 assistant `tool_calls` 与对应 tool 消息成组出现。拆开会导致 400 或语义错乱，所以压缩单位是完整工具交互组。单次模式固定 system policy 与原始任务；交互模式固定 system policy 与当前活动任务，旧轮次才允许压缩。

## 怎样支持人机交互？

`--interactive` 在同一 client、workspace 和 agent 上连续运行多轮：只有一轮正常返回后才提交其完整历史，用户下一条输入作为新 user 消息追加。每轮预算重置，但未验证修改的债务跨轮保留；`/quit` 和 `/exit` 由本地处理，不交给模型。

`--web` 是相同会话状态机的可视化适配层：左侧保留自然语言对话，右侧把 `model_request`、`tool_start`、`tool_end`、`warning` 和最终验证做成实时轨迹。浏览器从不持有原始历史或 API Key；刷新只重放后端有界事件，异常回合则安全关闭而不是猜测历史。

## 多个子 Agent 怎样协作？

`--subagents N` 可启用 `0..4` 个实验性只读子 Agent，默认 `0`。主模型把相互独立的调查合并成至多一批委派；批内子 Agent 使用线程并发，但每个都有独立的 DeepSeek client、history 和 context，只能调用列出、读取、搜索三个工具。结果限长并按输入顺序回到主上下文，子 Agent 的内部历史不会拼入主历史。

主 Agent 始终是唯一能写文件、执行命令、承担验证债务并决定任务完成的控制器。这样获得并行阅读收益，同时从能力层消除多个 Agent 并发写同一文件的冲突。子 Agent 不能递归委派；每个主任务至多一批，每个子 Agent 最多 6 步、24 次只读调用和 120 秒。

若调查期间工作区被外部修改，或所有子任务均失败，委派会以失败工具结果进入主历史；主 Agent 必须亲自重新读取工作区证据后才能结束。部分失败不会丢弃其他成功报告，整批输出仍受全局工具输出长度限制。

## 为什么不让子 Agent 直接修改代码？

共享工作区中的并发写入需要版本基线、冲突检测、回滚和合并仲裁，而简单加锁只能保证写入不同时发生，不能保证后一个 Agent 基于最新语义。当前版本把并发限制在调查阶段，由主 Agent 统一核对、修改和测试，边界更容易证明和答辩。若未来需要并行写入，应先给每个子 Agent 独立 Git worktree，再由主 Agent 审查 diff 和选择性合并。

## 子 Agent 的 120 秒能严格终止吗？

不能保证严格强杀。运行预算在模型调用边界检查，正在进行的 HTTP 请求仍由单次 request timeout 约束；Python 工作线程也不是进程级隔离。这里的“有界”指并发数、批次数、步骤数、只读工具数、结果长度和调用超时都有上限，不代表硬实时抢占。

## 这是沙箱吗？

不是。路径校验、无 shell 子进程、超时、密钥剥离以及子 Agent 的只读工具集都是减灾措施。主 Agent 允许执行的测试程序仍可能访问宿主权限范围，同机外部程序也可能修改工作区；强隔离必须依赖容器、虚拟机或 OS 权限机制。

## 为什么关闭 DeepSeek thinking？

V4 thinking 模式在工具多轮中要求回传 `reasoning_content`。本项目优先展示标准、可移植的原生工具循环，因此显式关闭；客户端仍保留服务端意外返回的该字段。

## 下一步如何扩展？

可增加容器执行后端、持久化检查点、结构化运行日志、人工审批级别和基于真实 token usage 的动态上下文预算。若扩展为可写子 Agent，应使用独立 Git worktree、基线哈希和主 Agent 合并仲裁，而不是放开共享目录写权限；这些扩展都不改变当前显式状态机。
